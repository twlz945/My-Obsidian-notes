# 控制反转

**控制反转（IoC）是一种设计思想，核心是将对象的创建、生命周期与依赖管理的控制权从业务代码转移至外部容器，而依赖注入（DI）则是实现这一思想的具体技术手段。**

## 🧠 核心思想：好莱坞法则

IoC 遵循“别找我们，我们找你”的原则。

- **传统模式**：业务代码主动通过 `new` 关键字创建依赖对象，导致代码高度耦合。
- **IoC 模式**：业务代码不再主动创建依赖，而是被动接收由外部容器（如 Spring 容器）在运行期动态注入的对象。

## 🛠️ 底层实现：工厂模式 + 反射机制

IoC 容器（如 Spring 的 `ApplicationContext`）通过以下机制落地这一思想：

1. **配置解析与注册**：容器读取配置元数据（XML、注解或 JavaConfig），解析出类名、作用域、依赖关系等信息，封装为 `BeanDefinition` 对象并注册到容器中。
2. **反射实例化**：容器根据 `BeanDefinition`，利用**反射机制**动态调用构造器创建对象实例，而非硬编码 `new`。
3. **依赖注入（DI）**：容器解析 `@Autowired` 等注解或配置，通过反射将依赖对象自动注入到目标对象的属性、构造器或 Setter 方法中。
4. **生命周期管理**：容器统一管理 Bean 的初始化（如执行 `@PostConstruct`）、增强（如 AOP 代理生成）以及销毁（如执行 `@PreDestroy`）。

## ⚙️ 核心优势

- **解耦**：高层模块依赖抽象接口而非具体实现，替换实现类无需修改业务代码。
- **可测试**：单元测试时可轻松注入 Mock 对象，隔离外部依赖。
- **可维护**：依赖关系集中由容器管理，代码结构清晰，遵循依赖倒置原则（DIP）。

## 📌 适用建议

- **推荐场景**：组件交互复杂的中大型应用、需要频繁进行单元测试的业务逻辑、可能更换底层实现的模块。
- **不推荐场景**：简单脚本、短期程序、依赖稳定且无需 Mock 的轻量级场景（直接 `new` 更简洁高效）。

简单理解：IoC 就像餐厅不再自己种菜，而是由供应商（容器）统一配送——餐厅专注做菜，随时可换供应商。
