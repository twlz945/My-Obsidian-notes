# 数据驱动设计

数据驱动设计指把**易变的数值与内容**从代码中抽离成数据（表格、JSON、配置），代码只负责解释数据。改内容时只换数据、不改代码，是游戏项目（尤其放置游戏）后期「改得动」的前提，对应需求 NFR-5。

## 核心要点

- **代码与内容分离**：逻辑稳定，数值独立演进。
- **可热更新**：换一份 [[JSON]] 即可生效，无需重新编译。
- **便于校验与工具化**：数据可用 schema 校验，也能用脚本批量生成。
- **策划/自己都能改**：降低修改门槛，减少硬编码 bug。

## 硬编码 vs 数据驱动

```typescript
// ❌ 硬编码：改配方要动代码
function smeltIron() {
  return { input: { ore: 1 }, output: { iron: 0.5 }, time: 3 };
}

// ✅ 数据驱动：数据在表里
type Recipe = {
  id: string;
  input: Record<string, number>;
  output: Record<string, number>;
  time: number;
};

function runRecipe(recipe: Recipe, state: State): State {
  // 通用逻辑，与具体配方无关
}
```

## 配方数据示例

```json
{
  "schemaVersion": 1,
  "recipes": [
    {
      "id": "iron_ingot",
      "input": { "iron_ore": 2 },
      "output": { "iron_ingot": 1 },
      "time": 3.2
    }
  ]
}
```

## 落地要点

- **统一 ID 与字段**：输入/输出用「物品 ID → 数量」映射，便于叠加与校验。
- **启动时校验**：检查字段类型、引用是否存在、数值范围（可借 [[Pydantic]]/Zod 思路）。
- **版本化**：数据带 `schemaVersion`，与 [[存档序列化与版本迁移]] 对齐。
- **工具生成**：后期用脚本从表格生成 JSON，避免手改出错。
- **缓存友好**：把数据表与运行状态分开，状态才需要存档。
