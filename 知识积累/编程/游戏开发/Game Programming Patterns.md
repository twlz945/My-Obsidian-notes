# Game Programming Patterns

《Game Programming Patterns》（游戏编程模式）由 Bob Nystrom 编写并在 gameprogrammingpatterns.com 免费发布，把经典设计模式翻译到游戏语境。`学习规划` 指定重点是**状态、组件、观察者、命令、对象池**。

## 核心要点

- **模式是工具不是目标**：先有痛点，再引入模式。
- **游戏特有的约束**：实时循环、海量对象、频繁变更、性能敏感。
- **与引擎呼应**：Godot 的节点/场景、资源系统本身就是若干模式的实现（见 [[节点与场景]]）。

## 重点模式

| 模式 | 解决的问题 | 放置游戏中的用途 |
| ---- | ---------- | ---------------- |
| 状态（State） | 对象行为随状态切换 | 机器「空闲/生产/堵塞」 |
| 组件（Component） | 用组合替代深层继承 | 机器 = 产出 + 耗电 + 存储组件 |
| 观察者（Observer） | 状态变化通知 UI | 数据变了刷新面板、解锁提示 |
| 命令（Command） | 把操作对象化 | 撤销、回放、宏操作 |
| 对象池（Object Pool） | 频繁创建销毁开销大 | 飘字、粒子、临时任务 |
| 类型对象（Type Object） | 数据定义「种类」 | 物品/配方/科技定义 |
| 更新方法（Update Method） | 每帧驱动一批对象 | [[固定步长循环]] 里的系统更新 |
| 子类沙盒（Subclass Sandbox） | 用基类原语组合行为 | 技能/效果脚本 |
| 服务定位器（Service Locator） | 全局访问服务 | 音频、存档、时钟 |

## 与数据驱动的关系

「类型对象」「组件」让行为由数据组合而成，是 [[数据驱动设计]] 的模式基础：数据描述「是什么」，模式描述「怎么跑」。

## 落地建议

- **不要预先套模式**：先写直白代码，出现重复或耦合再重构。
- **观察者优先**：[[数据驱动设计]] + 订阅刷新能显著简化 UI。
- **对象池只在真热时用**：过早优化有害。
- **模式与引擎对照**：用 Godot 时先看引擎是否已提供等价机制。
