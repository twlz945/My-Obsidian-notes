## TCP（Transmission Control Protocol）

**TCP** 是传输控制协议，属于 TCP/IP 协议栈中的**传输层协议**。 它是面向连接的、可靠的、基于字节流的通信协议，在不可靠的 IP 网络上提供可靠的端到端数据传输。

---

## 核心特性

|特性|说明|
|---|---|
|**面向连接**|通信前必须通过三次握手建立连接|
|**可靠传输**|通过确认、重传、序号机制保证数据不丢失|
|**有序交付**|通过序列号保证数据按发送顺序到达|
|**流量控制**|通过滑动窗口防止发送方压垮接收方|
|**拥塞控制**|通过慢启动、拥塞避免等算法防止网络过载|
|**全双工**|连接建立后双方可同时收发数据|

---

## 三次握手（建立连接）

TCP 通过三次握手建立可靠连接，同步双方初始序列号并确认双向收发能力。

```
客户端                          服务端
  │── SYN (seq=x) ──────────────>│  ① 客户端请求连接
  │<─ SYN+ACK (seq=y, ack=x+1) ─│  ② 服务端确认并回应
  │── ACK (ack=y+1) ────────────>│  ③ 客户端确认，连接建立
```

**为什么必须三次？** 两次握手无法防止历史过期连接请求造成资源浪费，也无法完整确认客户端的接收能力。 三次是理论最小值——服务端的 ACK 可以合并到 SYN 报文中一起发送。

---

## 四次挥手（断开连接）

TCP 是全双工通信，关闭连接需要双向独立确认。

```
客户端                          服务端
  │── FIN (seq=u) ──────────────>│  ① 客户端请求关闭
  │<─ ACK (ack=u+1) ────────────│  ② 服务端确认（可能还有数据要发）
  │<─ FIN+ACK (seq=w, ack=u+1) ─│  ③ 服务端数据发完，请求关闭
  │── ACK (ack=w+1) ────────────>│  ④ 客户端确认
```

**为什么是四次？** 服务端收到 FIN 后可能仍有数据未发完，ACK 必须立即回复，而 FIN 要等数据发完才能发送，二者无法合并。

**TIME_WAIT 的作用：** 主动关闭方进入 TIME_WAIT 状态等待 2MSL（最大报文段生存时间），确保最后一个 ACK 可靠到达，并让网络中残留的旧报文自然消亡，防止干扰新连接。

---

## 可靠传输机制

### 序列号与确认应答

每个 TCP 字节都有序列号，接收方通过 ACK 告知发送方已收到的数据位置。

```
发送方发送 seq=1000, len=500
接收方回复 ack=1500  （表示 1500 之前的字节都已收到）
```

### 重传机制

- **超时重传**：发送方为每个报文设置定时器，超时未收到 ACK 则重传。
- **快速重传**：收到 3 个重复 ACK 时，立即重传丢失报文，无需等待超时。

### 选择确认（SACK）

SACK 允许接收方告知发送方哪些不连续区间已收到，发送方只需补发真正缺失的部分，提高恢复效率。

---

## 流量控制与拥塞控制

### 滑动窗口（流量控制）

接收方通过 ACK 报文通告**接收窗口（rwnd）**，反映自身缓冲区剩余容量，防止被数据淹没。

### 拥塞窗口（拥塞控制）

发送方维护**拥塞窗口（cwnd）**，根据网络状况动态调整发送速率。

**实际发送窗口 = min(rwnd, cwnd)**

即发送方同时受接收方处理能力和网络承载能力的双重约束。

### 拥塞控制四大算法

|算法|行为|
|---|---|
|**慢启动**|cwnd 指数增长，快速探测可用带宽|
|**拥塞避免**|cwnd 线性增长，平稳增加负载|
|**快速重传**|收到 3 个重复 ACK 立即重传，不等超时|
|**快速恢复**|快重传后 cwnd 减半进入拥塞避免，避免速率骤降|

## TCP vs UDP

|维度|TCP|UDP|
|---|---|---|
|连接方式|面向连接（三次握手）|无连接|
|可靠性|可靠（重传、确认、序号）|不可靠|
|数据顺序|保证有序|不保证|
|数据形式|字节流|数据报|
|流量/拥塞控制|有|无|
|头部开销|20~60 字节|8 字节|
|适用场景|网页、文件传输、邮件、数据库|实时音视频、游戏、DNS、直播|

## 常见状态

|状态|含义|
|---|---|
|`LISTEN`|服务端监听端口|
|`SYN_SENT`|客户端已发送 SYN|
|`SYN_RCVD`|服务端已收到 SYN 并回复|
|`ESTABLISHED`|连接已建立|
|`FIN_WAIT_1/2`|主动关闭方等待对方 FIN|
|`CLOSE_WAIT`|被动关闭方等待应用层关闭|
|`TIME_WAIT`|主动关闭方等待 2MSL|
|`CLOSED`|连接已关闭|

## 常见问题

### 粘包问题

TCP 是字节流协议，没有天然消息边界。多次 `send()` 的数据可能被合并接收，或一次 `send()` 被拆分接收。

**解决方案：**

- 固定长度包
- 消息头携带长度字段
- 使用分隔符

### TIME_WAIT 积累

高并发短连接场景下，主动关闭方会积累大量 TIME_WAIT 连接，可能耗尽本地端口。

**优化手段：**

- 使用长连接 + 连接池
- 让 TIME_WAIT 落在客户端（服务端不主动关闭）
- 开启 `tcp_tw_reuse` 允许安全复用四元组

### SYN Flood 攻击

攻击者发送大量 SYN 但不完成三次握手，耗尽服务端资源。

**防御：** SYN Cookie、限制半连接队列大小等。

## 应用场景

- **Web 浏览**：HTTP/HTTPS 基于 TCP
- **文件传输**：FTP、SFTP
- **电子邮件**：SMTP、POP3、IMAP
- **数据库通信**：MySQL、PostgreSQL 客户端连接
- **即时通讯**：WebSocket 升级后基于 TCP 长连接
- **远程登录**：SSH、Telnet
